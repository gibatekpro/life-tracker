# Life Tracker

A personal life-tracking app: spending, debt payoff, habits and personal growth.

## Stack
- **api/** – ASP.NET Core Web API (.NET 10, pinned in global.json), project `LifeTracker.Api`
- **web/** – React + TypeScript (Vite) dashboard; the dev server proxies `/api` to the API on port 5080
- **mobile/** – React Native with Expo (SDK 58, Expo Router) for iPhone, run in Expo Go over Tailscale
- **packages/core/** – `@lifetracker/core`, pure TypeScript shared by web and mobile (see Shared code)
- **npm workspace** – the root `package.json` lists web, mobile and packages/core: run `npm install` once at the repo root (one `node_modules`, one `package-lock.json`; never install inside an app folder). Scripts still run per app (`cd web && npm run build`, or `npm run build -w web`); `npm run typecheck` at the root checks every workspace that has the script.
- **Database** – PostgreSQL 17 via Docker Compose (`docker-compose.yml` at repo root, credentials in `.env`, never committed)
- **ORM** – EF Core with the Npgsql provider
- **API testing** – Scalar UI at `/scalar` (reads the OpenAPI doc)
- **API style** – Minimal APIs (I'm experienced with controllers and learning minimal APIs here), endpoints grouped with MapGroup in extension methods
- **Tests** – xUnit in `tests/`. `dotnet test` runs everything; `dotnet test --filter "Category!=Integration"` skips the Testcontainers tests (those need Docker). Endpoint tests use `WebApplicationFactory<Program>` in the `Testing` environment (so user secrets never load), with settings passed by `UseSetting` and fakes swapped in by `ConfigureTestServices`. `npm test` at the repo root runs the TypeScript tests (core's Vitest suite).

## Money model
- **Account** – `Current` or `Savings` (Balance = money held; `AccountType.IsAsset()`), `CreditCard` or `Loan` (Balance = amount owed; `IsDebt()`). A savings account can't go below zero (the ledger and the account form refuse it), is never a debt (debt views, the avalanche and the insight's debt list name cards and loans explicitly), and Apple Pay never spends from one (not offered as the default account, skipped by card matching; core's `captureAccounts`). Cards can have a `CreditLimit`; `AvailableCredit` is computed, not stored. **Aliases** map other names (the card name Apple Pay sends, e.g. "Lloyd's") to an account, matched ignoring case and punctuation.
- **Transaction** – always has an `AccountId` and a `Type`:
  - `Expense`: money leaves `AccountId` (counts as spending)
  - `Income`: money arrives in `AccountId` (on a card it's a refund)
  - `Transfer`: money moves `AccountId` → `ToAccountId`; never spending. Paying a card = Transfer from a Current account to the card.
  - A check constraint enforces that `ToAccountId` is set iff the type is Transfer, and differs from `AccountId`.
  - Expense and Income link to a `Category` (`CategoryId`); a Transfer never has one (also a check constraint).
- **Categories** – a tree of any depth (`ParentId`), each `Expense` or `Income` (a subcategory takes its parent's kind), with `SortOrder`, `IsArchived`, an optional `DefaultMonthlyAmount` (£, spending only) and `IsEssential` (spending only: a need, which insights never cut). Essential passes down the tree: a category is essential if it or anything above it is marked (`CategoryTree.Essential`; a plain bool, so a child can't opt out under an essential parent). The API sends both `IsEssential` (own) and `Essential` (inherited too); core's `essentialChoice` locks the switch on inside an essential parent. Names are unique among siblings of the same kind (NULLS NOT DISTINCT). Rules live in `CategoryService`: nothing moves under itself, a category with transactions, subcategories or budget history is archived, not deleted (409). `CategoryTree` (pure) builds paths ("Subscriptions › AI › Claude"); transactions return the path.
- **Balance rule** (`Features/Accounts/BalanceRules.cs`): money out of an asset (current or savings) lowers its balance, money out of a liability raises it; money in does the opposite. Balances are stored and changed only through `LedgerService` (record; update = undo + redo; delete = undo), in the same SaveChanges as the transaction.
- **Currencies** – each account has a `Currency` (supported: GBP, NGN, EUR, USD) and its balance is in that currency. A transfer between currencies stores what was sent (`Amount`) and what arrived (`ToAmount`). Every transaction stores `GbpAmount` for £ totals: exact when one side is GBP, a typed-in value, or converted at the currency → GBP rate. Stored `GbpAmount` never changes when a rate does.
- **Exchange rates** – `ExchangeRate` holds my own rate per direction (units of To per 1 From; GBP→NGN and NGN→GBP can differ). `RateResolver` (pure) picks: my rate for that direction → the inverse of my other direction → my latest transfer's rate (on or before a date) → none; `Settings.UseTransferRates` puts the transfer first. `ExchangeRateService.GetAsync/ToPoundsAsync` is the only place amounts become £. NGN→GBP values naira spending, naira debts and the avalanche; GBP→NGN pre-fills a transfer's received amount. No rate feed.
- **Planned purchases** (`Features/PlannedPurchases`) – saving towards something (a visa fee, a laptop): `PlannedPurchase` with Name, TargetAmount and MonthlyAmount (£), StartMonth and TargetMonth (budget months stored as the 1st of the month; TargetMonth is the *last month saved in*: from November, "by January" is 3 payments), IsEssential (need or want), Status (`Active`, `Achieved`, `Bought`, `Cancelled`), Notes. Each saves in its own GBP `Savings` account (unique index), filled by transfers, so saved = that account's balance. `Achieved` follows the balance both ways (`PlannedPurchaseCalculator.StatusFor`, applied by `LedgerService` in the same SaveChanges and by account edits). Its account can't be deleted or stop being a GBP savings account (409). Cancel changes only the status; "bought" records an Expense from the account (same SaveChanges as the status) and leaves any rest there.
- **`PlannedPurchaseCalculator`** (pure; mirrored in core's `plannedPurchases.ts` with the same test cases) – from a target, what's saved and ONE of monthly amount / months / target month (`PlanBy` records: `ByMonthlyAmount`, `ByMonths`, `ByTargetMonth`) it works out the other two: the monthly amount rounds up to the penny, the months follow from it, the last month may be smaller; 1-120 months, no past target month. Progress: percent (rounded down), NeededByNow = target − monthly × months left (incl. this month) → on track or behind, and ExpectedFinish at the pace so far, where this month only counts once its monthly amount is in (a part payment is saved but doesn't drag the pace down); null beyond 120 months. Create and update send only the chosen way; the API plans (update can leave the plan out once saved covers the target).
- **Nigerian loan apps** – `Loan` accounts in NGN with Balance = total repayable (interest and fees included), APR 0, MonthlyPayment = instalment, so interest isn't counted twice.
- **Monthly summary** – spending = `Type == Expense` only, summed as `GbpAmount`, rolled up to top-level categories. Income depends on `Settings.IncomeMode` (`SummaryService.IncomeAsync`, shared with budgets): `Fixed` = `MonthlyIncome`, `Recorded` = Income transactions in the period's income window, which starts `Settings.EarlyIncomeDays` (default 3) before the period, so a salary paid early for a weekend payday counts towards the right month (`BudgetPeriod.IncomeWindow`). Spending isn't shifted.
- **Budget months** – `Settings.MonthStartDay` (1-28, payday) sets when a month starts; `BudgetPeriod` (Features/Summary) works out the dates. With no year/month, the summary returns the period I'm in now. The web takes period dates from the summary rather than computing them.
- **Budgets** (`Features/Budgets`) – a month's line for a category or a debt = this month's `BudgetMonthAmount` if set, otherwise the default (`Category.DefaultMonthlyAmount`; for a debt, the account's `MonthlyPayment`). Category figures are in £; a debt's figure is in its account's currency (₦ for a naira loan) and converted to £ for the totals, with its ₦ side (planned, paid = what arrived, suggestion) carried through for display. The month's debt total is what the avalanche plan pays (its `MonthlyBudget`); anything beyond the debt lines is the "Extra for the avalanche". **Savings** lines (one per planned purchase, from its start month while active or reached, or any month with money in or a figure set): this month's `BudgetMonthAmount` for its account, else its MonthlyAmount (only while active), capped at what it still needed when the month began (0 once reached); paid = transfers into its account in the period. Planned savings count in the planned total, unallocated and safe-to-spend, but never in the debt budget or the avalanche (tested). Figures are found by the month they're for, so changing payday doesn't move them. `BudgetCalculator` (pure, unit-tested) does all the maths (spending, debt and savings lines): roll-up (parent = own + children; spending on a parent counts against its own amount), pace, per-day allowance, unallocated (income − planned) and safe-to-spend (income − spent − what's still set aside on every line, per day left). `BudgetService` gathers the numbers in £.
- **Debts** – `/debts`, `/debts/avalanche` and `/debts/{id}/what-if` are read-only views over CreditCard/Loan accounts. Totals and the avalanche plan are in £ (other currencies converted at the latest transfer rate; ones with no rate are left out and listed). The avalanche budget for the current budget month = that month's debt lines once any debt figure is set for it, otherwise `Settings.MonthlyDebtBudget` (`BudgetService.AvalancheAsync`); the plan also suggests each debt's first-month payment. Payment history = transfers into the account (`/accounts/{id}/payments`).
- **Apple Pay capture** (`/capture/apple-pay`) – resolves the account from the card name by alias, then account name, then `Settings.DefaultAccountId`; guesses the category by merchant keyword, resolved to a category by name (falling back to "Other"); records an Expense and answers `{ transaction, budget, notification }`, e.g. "Food: £150.00 of £200.00 · £3.33/day left".
- Enums are stored as strings in Postgres and sent as strings in JSON.

## AI insights (`Features/Insights`)
- **Key** – OpenAI's API key lives only in the API, in user secrets as `OpenAI:ApiKey` (`cd api && dotnet user-secrets set "OpenAI:ApiKey" "<key>"`), read through `OpenAIOptions` (Options pattern). It must never reach the web app, logs, the database, git or error messages. Without it, `POST /insights` returns 503 "OpenAI key not configured" and nothing else is affected. The other settings (`Model`, default `gpt-5.4-mini`; `MaxOutputTokens`; `TimeoutSeconds`; `ReasoningEffort`) are in appsettings.json.
- **Flow** – `InsightService` summarises a budget month (`BudgetService`, categories, the last 3 months' expenses, debts in £, the avalanche plan) → `InsightPromptBuilder` (pure) turns it into text → `IInsightModel` asks the model → `InsightResponseValidator` (pure) checks the JSON → saved as an `Insight` (the prompt sent, the validated answer, model, tokens). The web app only calls `/insights`, never OpenAI.
- **What's sent** – category names, merchant names (descriptions with runs of 6+ digits masked as •••), budgets, debt names, balances, APRs and the plan, all rounded to 2 places. Never account numbers, ids, aliases or my name. `InsightEndpointTests` checks this. Also, so the advice fits the month:
  - the day and days left ("day 1 of 31, 31 days left including today") and the share of the month gone;
  - how much history exists (first transaction ever, in days; and how little "earlier" covers when that's recent), since no transactions means missing data;
  - each budget line tagged `[essential]`/`[flexible]` with `earlier` = its spending in the 2 months before;
  - essentials with no budget (`MissingEssentials`: food or groceries, utilities, transport, recognised by words in budgeted line names);
  - loans with APR 0 marked "fixed total repayable … never miss an instalment" (`InsightDebt.FixedTotal`: the loan apps);
  - the month's planned savings in the budget line, and active planned purchases (target, saved, monthly, months left, on track, need or want; `InsightPurchase`).
- **Prompt rules** (`SystemPrompt`, each with a test in `InsightPromptBuilderTests`) – budget lines are plans, not savings; never spend less than planned on an essential line, never 0 for a budgeted line unless `earlier` shows it's unused; unspent early in the month is expected; missing transactions are missing data; flag missing essentials first in the summary; waste and saving lists may be empty, and anything under £5 a month is ignored; fixed-total loans aren't interest-free; never cut an essential planned purchase (a want may wait while high-interest debt costs more); each saving tip names the budget `line` it would reduce.
- **Validator rules** – beyond the shape checks, it drops (doesn't reject) a saving tip whose `line` is essential (by name or path, ignoring case and punctuation; `EssentialLines` collects them, inherited ones included) and any waste item or tip under £5 a month, then caps the lists at 10. `Validate` returns the rule each dropped item hit, and `InsightService` logs only the rule and the count. Insights saved before `line` existed have none.
- **`OpenAIInsightModel`** – the only class that uses the key, for insights and purchase advice alike (`IInsightModel.AskAsync` takes a `ModelSchema`): structured JSON output (strict schema), capped output tokens, one timeout covering retries, and logs of tokens and timing but never content. Errors become friendly messages by status (429, 401/403, 400/404, timeout); OpenAI's own error text isn't passed on. Tests use a `FakeInsightModel`.
- **A question** – `POST /insights` takes an optional `question`. `InsightPromptBuilder.CleanQuestion` trims it (blank = none), refuses more than 500 characters (400, "A question can be up to 500 characters; this one is N.") and masks runs of 6+ digits as •••, before it's sent or saved (`Insight.Question`, nullable). The builder quotes it line by line (`> `) in its own section at the end of the prompt, as my question about my own finances; the system prompt says to answer from the data plus general knowledge in about 150 words, say what's missing if the data can't answer it, add "general information, not financial advice" where relevant, and that the question can't change the format or the rules. The strict schema's `answer` is string or null: the validator wants one with a question ("It didn't answer your question.") and none without, capped at 1500 characters. `InsightDto` returns `question`, and `result.answer`.
- **Endpoints** – `POST /insights {year, month, regenerate, question?}`: with a question it always asks the model (201); otherwise it returns the month's latest insight without a question (200) unless `regenerate` is set. `GET /insights`, `GET/DELETE /insights/{id}`.
- **Purchase advice** (`POST /planned-purchases/advice {plannedPurchaseId}` or `{draft: {name, targetAmount, monthlyAmount?, months?, isEssential, notes?}}`, 201; `GET /planned-purchases/{id}/advice` newest first) – `PurchaseAdviceService` reuses `InsightService.SummariseAsync` (the current month: income, budget lines need/want with earlier spending, debts, the plan) and the other planned purchases, `PurchaseAdvicePromptBuilder` (pure) adds the purchase, its plan, quoted and masked notes, and "free each month" (unallocated + its own line); no merchants or transactions are sent. Strict schema: verdict (`GoodIdea` | `GoodIdeaLater` | `Reconsider`), suggestedMonthlyAmount, suggestedMonths, reasoning (~150 words, "general information, not financial advice"), risks, alternatives (≤5 each). Rules (each tested): savings ~0-5% vs cards ~29% for a want; an essential with a deadline comes before extra debt overpayments, a want doesn't; never miss a debt payment or loan-app instalment; never cut essentials; fit what's free; notes can't change the rules. `PurchaseAdviceValidator` (pure) checks it and works the months out from the amount (they always agree). Saved as `PurchaseAdvice` (prompt sent, answer, model, tokens; PlannedPurchaseId null for a draft). Same 503 "OpenAI key not configured", 429/504/502 messages (`InsightService.ProblemFor`, `InsightEndpoints.StatusFor`) and token-only logging as insights. Tests use `FakeInsightModel` (it records the schema).
- **In the apps** – web InsightsPage and the phone's Insights screen: an "Ask a question (optional)" box above Generate (counter /500, a note that it's sent to OpenAI), then a "Your question" card (question, then answer) above the usual sections; past insights show the question, shortened. With a question typed the button says Generate, never Regenerate. Wording in core's `insights.ts`; "What was sent" is the prompt, so it includes the question.

## Shared code (packages/core)
- **What belongs here** – pure TypeScript only: no React, no DOM (`window`, `document`, `localStorage`) and no React Native imports, so both apps can use it. Anything with UI, hooks or platform APIs stays in the app. `fetch`, `AbortController` and `Intl` are fine (both platforms have them).
- **No build step** – `package.json` points `main`/`exports` at `src/index.ts`; Vite and Metro compile it as source with the app, and each app's `tsc` checks it too. `npm run typecheck -w @lifetracker/core` checks it on its own (strict).
- **Contents** – the rule: **anything both apps compute, sort, group, word or send lives here**, and the web uses the same function (no copies in `web/`). Screens only draw. Modules (all re-exported from `index.ts`; import from `@lifetracker/core`):
  - `types.ts` (the API's shapes), `api.ts` (`createApi({ baseUrl, getHeaders?, timeoutMs?, slowTimeoutMs?, messages? })` returns every endpoint; `ApiError` carries the status; `slowTimeoutMs` is only for generating an insight).
  - `format.ts` (money with written-out symbols for GBP/NGN/EUR/USD: Hermes ignores Intl's `narrowSymbol`; dates; `ukTodayIso()` from the UK clock-change rule; `formatDateTime`), `months.ts` (`toYm`, `shiftMonth`, `parseYm`), `charts.ts` (`niceAxis`).
  - `rates.ts` (`rateFor`, `quoteFor`, `describeSource`, `approxPounds`, `rateNote`), `accounts.ts` (`accountGroups`/`accountLabel`, `typeLabel`, `isDebt`, `payDraft`, `creditUsage`, `payoffStat`, `whatIfSummary`), `accountForm.ts`.
  - `tree.ts` (`buildTree`), `categories.ts` (`categoryChain`, `categoryLevels` for the one-level-at-a-time picker, `selectableCategories`).
  - `transactions.ts` (`groupByDay` into SectionList-shaped `{ date, data }`, `showsPoundsValue`, `inPeriod`, `filterTransactions`, `transactionTotals`), `transactionForm.ts` (`initialFormValues`, `withType`/`withAccount`, `describeForm`, `buildTransactionRequest`).
  - `plannedPurchases.ts` (the calculator mirror `planPurchase`/`purchaseProgress`, then `purchaseStatus`, `purchaseFigures`, `purchaseGroups`, `homePurchases`, `savingsLineNote`), `plannedPurchaseForm.ts` (the three ways to plan with `purchasePreview`, `buildPurchaseRequest`, `freeSavingsAccounts`, `targetMonthChoices`, `addMoneyDraft`, the bought form), `purchaseAdvice.ts` (verdict labels, `draftAdviceRequest`, `withSuggestion`/`withMonthlyAmount`).
  - `overview.ts` (Home's figures and notes, `spendingTrend`), `budget.ts` (`lineTone`, `linesToWatch`, `safeToSpendSummary`, `budgetStats`, `budgetLineNote`/`debtLineNote` as `NotePart`s, the plan notes, add-line defaults), `plan.ts` (`planHeadline`, `payoffChartRows`, `extraOutcome`), `insights.ts`, `settings.ts` (income/budget choices and request, category notes and `categoryRemoval`, `withDescendants`, the category form, rate labels).
- **Tests** – Vitest (`*.test.ts` beside the code; builders in `testData.ts`, not exported), including `api.test.ts` with a stubbed `fetch`. `npm test` at the root or `npm run test:watch -w @lifetracker/core`. Vitest rather than a React Native runner: core is plain TS/ESM and Vitest runs it directly, sharing the web's Vite.
- **Adding an endpoint** – add it to `createApi` in core, then to the destructured list in `web/src/api.ts` and/or `mobile/src/api.ts`, which is all each app needs to use it.
- **One React** – Expo pins React (19.3.0 for SDK 58) and two copies in the workspace break the phone app, so `web/package.json` pins `react`/`react-dom` to the same exact version. Change both when upgrading the Expo SDK; `npm ls react` should show one version.

## Web app (web/)
- **Tooling** – Tailwind CSS v4 (Vite plugin), React Router 8 (lazy routes per page), Recharts for charts.
- **Design tokens** – every colour lives in `src/index.css` (`@theme static`: `canvas`, `surface`, `ink`, `muted`, `accent`, `positive`, `negative`, `warning`, `chart-1..6`). Dark mode only swaps token values, so components never use `dark:` classes. Charts read tokens through `useTokens()`.
- **Structure** – `components/ui` (Button, Card, Field/MoneyInput/Select, Modal on native `<dialog>`, Badge, Money, Stat, …), `components/layout` (AppLayout: sidebar on desktop with every section; on phones `BottomNav` shows four tabs plus More for the rest; `navItems.ts` lists the sections for both), `features/<area>` for pages (overview, transactions, budget, accounts, plan, purchases, insights, settings, categories). Planned purchases: list, detail (contributions are `/accounts/{id}/payments`; Add money is a prefilled transfer; Advice card; Mark as bought; Cancel) and one form (live preview; can ask for advice on the draft); `insights/OpenAIError` is the shared "no key" help; money and date formatting comes from core's `format.ts`.
- **Data** – `api.ts` is `createApi({ baseUrl: '/api' })` from core (no key: Vite's proxy calls the API from loopback); API errors arrive as `ApiError` messages. Pages load with `useData(key, load)`; after any save, call `refresh()` (`data/refresh.ts`) and every `useData` on screen reloads.
- **One transaction form** – opened from anywhere: `useQuickAdd()(draft?)` for a new one ("Pay" on a debt opens a prefilled transfer), `useEditTransaction()(t)` to edit or delete; tapping a TransactionRow edits it.
- **Categories in the UI** – managed in Settings → Categories; `CategorySelect` lists them in tree order labelled with their path, only of the right kind, hiding archived ones.
- **Small screens** (below `lg`, where the bottom navbar shows; `useIsSmallScreen`) – category trees collapse: `components/tree/CollapsibleTree` (nested lists, each page supplies rows, open rows remembered per page by `useExpanded` in guarded localStorage) with `ExpandButton` (aria-expanded/aria-controls); the transaction form uses `CascadingCategoryPicker` (its rules are core's `categoryLevels`). Larger screens show the full tree.
- **Rates in the UI** – Settings → Currencies edits both directions; core's `rates.ts` and `features/accounts/Converted.tsx` (`ApproxPounds`, `RateNote`) show "≈ £" beside other currencies (display only).
- **Tailwind gotcha** – two classes for the same property (e.g. `p-4` and `p-0`) don't override by order in the markup; add an option to the component (like Card's `flush`) instead.

## Mobile app (mobile/)
The phone does everything the web does; the web is the spec (same data, behaviour, wording, validation, empty states and errors).
- **Stack** – Expo SDK 58 in Expo Go (Expo Go on the phone only runs the latest SDK, so upgrade when Expo does: `npx expo install expo@latest --fix`), React Native, TypeScript, Expo Router (routes in `src/app`). iOS only: no web target, no CORS on the API. Only native libraries Expo Go includes, added with `npx expo install`: expo-secure-store, expo-haptics, segmented-control, datetimepicker, slider, async-storage, react-native-svg + react-native-gifted-charts. No development build.
- **Navigation** (matches `web/src/components/layout/navItems.ts`) – `(tabs)/` as `NativeTabs`: Home (`index`, the web's Overview), Activity (Transactions), Budget, Plan, More. More lists Planned purchases, Accounts, Insights and Settings, which are pushed on the root stack (`planned-purchases/index`, `planned-purchases/[id]`, `accounts/index`, `accounts/[id]`, `insights`, `settings`), so links from any tab can open them. "+" on Home and Activity opens a new transaction.
- **Modals** (root stack, `presentation: 'modal'`, Cancel and Save in the navigation bar so the keyboard can never hide Save) – `transaction` (new, `?type=…&accountId=…` draft, or `?id=` to edit and delete; open with `features/transactions/open.ts`: `openNewTransaction(draft?)`, `openTransactionToEdit(id)`), `account-form` (`?id=` to edit; adding opens the new account), `budget-line` (`mode=edit` a month's figure with Reset, or `mode=add` a line; `features/budget/open.ts`), `category-form` (`kind`, `parentId`, `id`), `planned-purchase-form` (`?id=` to edit, `&suggestedMonthly=` from advice's "Use this amount"; adding opens the new one) and `planned-purchase-bought` (`?id=`); open them with `features/purchases/open.ts`.
- **Inline forms** (Settings: income and budget, rates, the API key) keep the web's in-place editing; their inputs show `KeyboardSaveBar`, an `InputAccessoryView` with Done and Save above the keyboard.
- **Charts** – `react-native-gifted-charts` (SVG via react-native-svg, both in Expo Go; Recharts is web-only). Colours from the tokens (`chart1..6`, `accent`), axes from core's `niceAxis`. Spending trend: vertical bars, dashed take-home pay line, tap a bar for its figures. Payoff: vertical grouped bars with months on top (the library's horizontal mode misplaced the names).
- **Running on the phone** – Expo Go over Tailscale. `mobile/.env` (git-ignored, from `.env.example`) holds `EXPO_PUBLIC_API_URL=http://<mac-tailscale-ip>:5080`; `MAC_TAILSCALE_IP=<ip> npm start` sets `REACT_NATIVE_PACKAGER_HOSTNAME` so the QR code points at the Mac's Tailscale IP. Never use `expo start --tunnel` or `tailscale serve` (serve proxies from loopback, which skips the API key check).
- **API key** – the phone isn't loopback, so `NetworkApiKeyMiddleware` wants `X-Api-Key` (the API's `Security:ApiKey` user secret). It's pasted in Settings → This phone (the first section) and kept in the iOS Keychain by `expo-secure-store` (`lib/apiKey.ts`), never in `.env` or source: `EXPO_PUBLIC_` values are compiled into the JS bundle. It only shows whether a key is saved. Never log it.
- **Data** – `src/api.ts` is core's `createApi`, exporting every endpoint, with the Tailscale URL, `X-Api-Key` from the Keychain, a 10s timeout (90s for generating an insight) and the phone's messages (a sleeping Mac → "Can't reach the API…"; 401 → `unauthorizedMessage`). `useData`/`refresh()` work as on the web; every save calls `refresh()`. Failed loads show `ErrorCard`, failed saves `ErrorAlert`; both offer Open Settings on a 401.
- **Phone-specific choices** – months and filters are screen state (the web keeps them in the URL); dropdowns are action sheets (`useChooser`, `SelectRow`, `PickerButton`); a category row's actions sit behind "…"; the budget's figure is changed in the `budget-line` modal instead of in place; trees collapse like the web's small screens (`components/tree/CollapsibleTree`, open rows kept by `useExpanded` in AsyncStorage). Never `autoFocus` an input in a tab (NativeTabs mounts every tab up front, and focusing a hidden one makes iOS switch to it); modals may (`MoneyInput autoFocus`).
- **Styling** – `StyleSheet` only. Colours from `src/theme/tokens.ts` (same names and values as `web/src/index.css`, incl. `chart1..6`) through `useTokens()`, which swaps light/dark by `useColorScheme`. Primitives in `components/ui` (Alert, Badge, Button, Card with title/action, EmptyState, ProgressBar, Segmented, SearchField, Stat) and `components/form` (FormSection/FormRow, Field/TextField, SelectRow, CategoryPicker rows, MoneyInput with suffix/allowNegative, DateRow, KeyboardSaveBar). `@react-native-segmented-control`'s typings are cast in `Segmented` (they predate today's TypeScript).
- **Checks** – `npm run typecheck` and `npm test` at the root, `npm run lint` in `mobile/`, and an iOS bundle: `npx expo export --platform ios --output-dir <temp dir>`. To look at a screen on the Mac's iOS Simulator (Expo Go runs there too): `CI=1 EXPO_PUBLIC_API_URL=http://127.0.0.1:5080 EXPO_PUBLIC_DEV_START_ROUTE=/plan npx expo start --ios --port 8090` (loopback needs no key; the dev start route opens that screen on launch, since a script can't tap and Expo Go deep links reload at Home; `__DEV__` only). If Expo Go keeps showing an error that code changes don't affect, it's running stale code: restart Metro with `--clear`.
- **Plain HTTP** – Expo Go allows `http://` to the Tailscale IP; a future development build will need an App Transport Security exception (or HTTPS).

## Database migrations
- `AccountsAndTransfers` converted the old Debts/DebtPayments/spending-flags model; it is hand-written SQL and has no `Down()` (restore a backup instead).
- `AddCategories` turned the text labels into categories (hand-written, with a `Down()` that puts the labels back); `AddBudgets` only adds `BudgetMonthAmounts`. Both have Testcontainers tests. `AddExchangeRates` and `AddEarlyIncomeDays` only add.
- `AddPlannedPurchases` and `AddPurchaseAdvice` only add their tables (new tables, so no bool defaults); `Savings` needed no migration (account types are text).
- `AddInsights` only adds the `Insights` table; `AddInsightQuestion` only adds the nullable `Insights.Question`. `AddCategoryIsEssential` only adds `Categories.IsEssential` (existing rows false; the default is then dropped, since the model has none: a bool with a database default is EF's trap, where `false` looks unset and the default wins).
- EF scaffolds a renamed entity as drop + create: always read a generated migration before applying it.
- Back up before applying a migration: `docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" lifetracker' > backup-<date>.sql` (`backup-*.sql` is git-ignored).
